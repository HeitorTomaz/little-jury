# Outputs

Everything goes in `rounds/v<version>/`, written in the language set in `config.md` (`- Language:`). For the criteria family, `method/rounds-criteria.md` ("Round 5") says how each file below reads for a work judged against criteria: no overall verdict by majority, the tally and the divergences per criterion.

**Two readers, two formats:**

- **`report.html` is the deliverable for the author.** It is the only file they need to open. Everything they need in order to decide (conclusions, disagreements, what to test first, risks, the panel's limits) must be there.
- **The `.md` files are for Claude**: the panel's memory for a future session that picks the project up again, compares versions or helps the author decide. Write them for that reader: complete, with each persona's positions by `id`, the classification of each claim and the reference to the round file and section it came from (`r2.md`, section `designer`), without summarizing so much that who said what gets lost.

## Round files (saved unedited)

One file per round, with one section per persona (a `## <id>` heading, then `- Model: <model> (<agent type>)` and `- Date: <date>`, then the answer). Many separate files are hard to read and to attach.

| File | Origin |
|---|---|
| `r1.md` | round 1, one section per user |
| `r2.md` | round 2, one section per agent |
| `list-draw.json`, `list-rankings.json`, `list-analysis.json` | list draw, rankings and analysis, if active |
| `r3-scenarios-proposed.md`, `r3.md` (one section per participant), `r3-scenarios.md` | round 3 |
| `r4-contrarian-pack.md`, `r4-contrarian.md` (both calls and the requested answers), `r4-agenda.md`, `r4-debate-replies.md` (one `## <point> — <id> — turn <n>` section per reply), `r4-debate.md` | round 4 |
| `prompts/` | exact prompt of each call, one file per call |
| `inputs-used/` | snapshot of the inputs |
| `progress.md` | status and call log |

## Final files (round 5)

| File | Content |
|---|---|
| `concept-review.md` | The panel's synthesis: what the proposal is according to the panel, whom it seems to serve and whom it does not, the 3 to 5 main findings, what remains open. A separate section lists the **pitch problems** from the comprehension check: problems of the text, not of the project. When the audience is undefined, it says what each group wants and what choosing each would cost, without tallying them together |
| `strengths-and-risks.md` | Strengths and criticisms, each with evidence (file and persona, with the source as `(r2.md § <id>)`), classification (observation, hypothesis, proven problem) and uncertainties. Each strength also says **who opposed it, and why** (or that nobody did). Same-model duplicates count as one piece of evidence, and the destroyer and the contrarian are not counted as agreeing voices |
| `design-alternatives.md` | Starts with the **quick wins, grouped by debate point** (the smallest change to a rule or decision that would solve each point): for each, the change, what it solves, what is lost, who proposed it, who supported it and who opposed it (from the debate replies, plus the experts' round 2 answers). Then the larger suggested changes; each one says **what problem it solves, what benefit it expects and what is lost**, who defended it and who disagreed. Check all of them against the author's decisions that limit the recommendations (`config.md`) |
| `mvp-hypotheses.md` | Hypotheses only real people can answer, with a minimal test within the author's means, a confirmation signal and a priority |
| `comparison.md` | Re-evaluation only: each earlier problem (P1, P2… from `moderator/previous-problems.md`) as resolved, partly resolved or unresolved, with the evidence from this run; then the new problems the changes created |
| `list.md` | If active: the panel's final order, the individual rankings with the order in which each agent received the list, rejections, order effect, arguments, and what the expert with web access found or could not check |
| `diversity.md` | Evaluation of the panel itself; guide in `method/diversity.md` |
| `report-data.json` | Data for the visual report |
| `report.html` | Visual report, generated by the script, with the `fonts/` folder next to it |

**Never recommend running the panel again**, in any file or in the report: whether to run another panel is the author's decision.

## List analysis

Save the rankings in `rounds/v<version>/list-rankings.json`, in the format `{"<id>": ["1st item", "2nd item", ...], ...}`, with the names exactly as they appear on the list, and a `"rejections": {"<id>": ["item", ...]}` key if there are any. Then:

```bash
python method/scripts/analyze_list.py rounds/v<version>/list-draw.json rounds/v<version>/list-rankings.json --output rounds/v<version>/list-analysis.json
```

The script computes each item's average position, how many first places each one got, the rejections and the order effect (how many agents put first the item they received on the first row, against what chance would give), item by item. Analyze name by name: in the pilot, the leader resisted the order effect; it was the competitors' first places that were inflated.

## Visual report

The template is in `template/report-template.html`. **Do not edit the HTML.** Write the data in `rounds/v<version>/report-data.json` and run:

```bash
python method/scripts/report.py build rounds/v<version>/report-data.json --template template/report-template.html --output rounds/v<version>/report.html
```

The script validates the data, inserts it into the `<script type="application/json" id="panel-data">` block, checks that the rest of the file is identical to the template and copies the `fonts/` folder next to the report. If validation fails, fix the JSON and run it again. Do not open a browser: the session that launched the run opens the report for the author.

The template's example data is fictitious and neutral ("User A", "Item A"). Do not reuse any of it.

### Fields

| Field | Origin |
|---|---|
| `meta.example` | always `false` |
| `meta.concept`, `meta.version`, `meta.date` | `config.md` and the run date |
| `meta.panelSize` | "lean panel" or "full panel", in the report language |
| `meta.composition` | the actual panel, for example "8 users, 4 experts and 2 adversaries" |
| `meta.domain` | domain from `config.md` |
| `meta.type` | `"concept"`, `"system"`, `"change"` or `"work"`, from `config.md`; changes the sentence at the top of the report |
| `meta.family` | optional, default `"audience"`; `"criteria"` when `config.md` says `- Family: criteria`. It switches the stances grid, its legend, the conditions list and the quick wins intro to the criteria wording (the `*Criteria` labels: "Each juror, criterion by criterion", "meets", "only if revised", "does not meet", "Bench") without changing any enum value |
| `meta.usersLabel` | what the domain calls its users ("Users", "Players", "Readers", "Students"; in the criteria family "Jurors", "Reviewers" or "Committee"), in the report language |
| `meta.language` | the language from `config.md` (e.g. `English`, `Brazilian Portuguese`) |
| `meta.audienceDefined` | optional, default `true`; `false` when `config.md` says `- Defined: no` under `## Audience`. It hides the panel tally row of the stances grid, because tallying together profiles that want opposite things says nothing |
| `summary` | 3 to 5 conclusions from the moderator, one sentence each |
| `dimensions` | those in `config.md`, with the same `id`, in round order. Each has `id`, `name` and `question` (the question from `config.md`). In the criteria family they are the **criteria** ("Does the work meet <criterion>?"). The **last** one colors the seats of the table at the top of the report by stance (willingness to try or to accept; in the criteria family, the last criterion) |
| `users[]` | `id`, `name`, `profile` (one line), `model`, final `stances`: `{"<dimension id>": {"stance": "yes" | "only if" | "no" | "does not apply", "condition": "...", "reason": "..."}}`, with round 2 stances for that round's dimensions and, for the round 1 dimension (curiosity, or relevance for a change), the stance revised in round 2 when the persona revised it, otherwise the round 1 stance; `condition` is required for `only if`, `reason` is optional (one sentence); `understood`, `attracted`, `putOff`, `dropOut` (one sentence each, from rounds 1 and 2). There is no clarity stance: comprehension goes to `pitchIssues`. In the criteria family the same four fields hold the juror's reading of the work, its strongest part, its main weakness and the revision that would change their verdict most (`rounds-criteria.md`, round 5) |
| `pitchIssues[]` | optional; the pitch problems from the comprehension check: `sentence` (the sentence or idea of the pitch), `intended` (what it meant to say), `understoodAs` (how it was understood), `who` (ids). Only sentences that half of the users or more understood differently. The section is hidden when the list is empty or absent |
| `comparison[]` | optional, re-evaluation only: `problem`, `status` (`resolved`, `partly`, `unresolved` or `new`), `note` (the evidence from this run). Hidden when absent |
| `tensions[]` | disagreements from the debate and from round 2: `title`, `evidence`, `severity` (1 to 3), `for` and `against` with `who` (ids) and `text`, `proposal`, `loss`, `experiment`. Reactions to a revenue model go here |
| `quickWins[]` | the quick wins from the debate (the smallest changes proposed; in the criteria family, the smallest revisions to the work that change a verdict), one entry per proposal: `point` (the debate point, as a short title), `change`, `solves`, `loss`, `proposedBy`, `support` and `against` (ids). Merged proposals list every proposer. Ordered by point; inside a point, the report sorts by support |
| `audienceSplit[]` | optional, when the audience is undefined: `group`, `wants`, `who` (ids), `cost` (what choosing this group as the audience would cost). Hidden when absent |
| `risks[]` | `title`, `category` (`design`, `audience`, `production`, `scope` or `market`), `severity` and `likelihood` (1 to 3), `description`, `who` |
| `strengths[]` | `title`, `description`, `who`; optional `opposedBy` (ids) and `opposition` (one sentence: why they opposed it) |
| `experts[]` | `id`, `role`, `opinion`, `mainProblem`, `recommendation` |
| `adversaries[]` | `id`, `role`, `arguments[]` with `title` and `text` |
| `scenarios[]` | round 3: `situation`, `outcome`, `classification` (`"hypothesis"` or `"proven problem"`). In the criteria family, `situation` is the claim and the objection, `outcome` whether the work answers it |
| `hypotheses[]` | `hypothesis`, `test`, `signal`, `priority` (`high`, `medium` or `low`) |
| `launch` | optional; omit it if it was not asked. `title`, `intro`, `recommendation`, `reasons[]`, `preferences[]` (`who`, `where`), `caveats` |
| `list` | optional; omit it if inactive. `title`, `order[]` with `name`, `comment`, `first` (ids), `rejected` (ids); `note` with the conflicts found and what stayed **[not verified]** |
| `gaps[]` | everything the panel could not evaluate for lack of specification |
| `limits[]` | 2 to 4 sentences from `diversity.md` on the limits of this run (anchoring, convergence, order effect) |
| `labels` | optional in English; **required, with every key**, when `meta.language` is not English. See below |

Conventions:

- Stances: `"yes"`, `"only if"` (always with its `condition`) or `"no"`. In the criteria family the values are the same and mean meets, meets only with the revision in `condition`, and does not meet; `reason` carries the reason and the passage of the work quoted. They replace the 1-to-5 scores of earlier versions: in a real run, every score fell between 2 and 4 and several users answered 3/3/3, which said nothing a condition would not say better. `"does not apply"` (always with its `reason`) is for a question that does not fit the persona's relation to the project; it stays out of the tally.
- **Enum values stay in English** whatever the report language: `evidence` only accepts `"observation"`, `"hypothesis"` or `"proven problem"`; `classification` only `"hypothesis"` or `"proven problem"`; `priority` only `high`, `medium` or `low`; `category` one of the five above; `meta.type` one of the four above; `meta.family` only `audience` or `criteria`; `comparison[].status` only `resolved`, `partly`, `unresolved` or `new`; `stance` only `yes`, `only if`, `no` or `does not apply`. The page shows them through the labels.
- Every `who` (including those of `pitchIssues` and `audienceSplit`), `opposedBy`, `first`, `rejected`, `proposedBy`, `support`, `against` and `preferences[].who` uses ids that exist in `users`, `experts` or `adversaries`.
- All free text (summary, titles, descriptions, names, comments) is written in the report language.

### Report labels

The template holds a second JSON block, `<script type="application/json" id="default-labels">`, with every interface string in English: section titles and intros, buttons, legend, the names of the evidence values, priorities and risk categories, the risk axis names, the footer, the example-data notice. Composed strings use `{placeholders}` (for example `"metaLine": "Evaluated on {date} by a {panelSize} of {composition}."`); keep every placeholder when translating.

- The page uses `labels[key]` from the data when present, and the default otherwise.
- When `meta.language` is not English, copy **every** key of the `default-labels` block into `labels`, translated into that language. `report.py` reports an error if a key is missing or if `labels` has a key the template does not know.
- Never edit the `default-labels` block: it is part of the template, and the script checks that it stayed identical.
