# Outputs

Everything goes in `rounds/v<version>/`, written in the language set in `config.md` (`- Language:`).

**Two readers, two formats:**

- **`report.html` is the deliverable for the author.** It is the only file they need to open. Everything they need in order to decide (conclusions, disagreements, what to test first, risks, the panel's limits) must be there.
- **The `.md` files are for Claude**: the panel's memory for a future session that picks the project up again, compares versions or helps the author decide. Write them for that reader: complete, with each persona's positions by `id`, the classification of each claim and the reference to the round file it came from (`r2-designer.md`), without summarizing so much that who said what gets lost.

## Round files (saved unedited)

| File | Origin |
|---|---|
| `r1-<id>.md` | round 1, one per user |
| `r2-<id>.md` | round 2, one per agent |
| `list-draw.json`, `list-rankings.json`, `list-analysis.json` | list draw, rankings and analysis, if active |
| `r3-scenarios-proposed.md`, `r3-<id>.md`, `r3-scenarios.md` | round 3 |
| `r4-contrarian-pack.md`, `r4-contrarian.md`, `r4-agenda.md`, `r4-<point>-<id>-v<turn>.md`, `r4-debate.md` | round 4 |
| `prompts/` | exact prompt of each call |
| `inputs-used/` | snapshot of the inputs |
| `progress.md` | status and call log |

## Final files (round 5)

| File | Content |
|---|---|
| `concept-review.md` | The panel's synthesis: what the proposal is according to the panel, whom it seems to serve and whom it does not, the 3 to 5 main findings, what remains open |
| `strengths-and-risks.md` | Strengths and criticisms, each with evidence (file and persona), classification (observation, hypothesis, proven problem) and uncertainties |
| `design-alternatives.md` | Suggested changes; each one says **what problem it solves, what benefit it expects and what is lost**, who defended it and who disagreed. Check them against the author's decisions that limit the recommendations (`config.md`) |
| `mvp-hypotheses.md` | Hypotheses only real people can answer, with a minimal test within the author's means, a confirmation signal and a priority |
| `list.md` | If active: the panel's final order, the individual rankings with the order in which each agent received the list, rejections, order effect, arguments, and what the expert with web access found or could not check |
| `diversity.md` | Evaluation of the panel itself; guide in `method/diversity.md` |
| `report-data.json` | Data for the visual report |
| `report.html` | Visual report, generated by the script, with the `fonts/` folder next to it |

## List analysis

Save the rankings in `rounds/v<version>/list-rankings.json`, in the format `{"<id>": ["1st item", "2nd item", ...], ...}`, with the names exactly as they appear on the list, and a `"rejections": {"<id>": ["item", ...]}` key if there are any. Then:

```bash
python method/scripts/analyze_list.py rounds/v<version>/list-draw.json rounds/v<version>/list-rankings.json --output rounds/v<version>/list-analysis.json
```

The script computes each item's average position, how many first places each one got, the rejections and the order effect (how many agents put first the item they received on the first row, against what chance would give), item by item. Analyze name by name: in the pilot, the leader resisted the order effect; it was the competitors' first places that were inflated.

## Visual report

The template is in `template/report-template.html`. **Do not edit the HTML.** Write the data in `rounds/v<version>/report-data.json` and run:

```bash
python method/scripts/report.py build rounds/v<version>/report-data.json --template template/report-template.html --output rounds/v<version>/report.html
```

The script validates the data, inserts it into the `<script type="application/json" id="panel-data">` block, checks that the rest of the file is identical to the template and copies the `fonts/` folder next to the report. If validation fails, fix the JSON and run it again. Do not open a browser: the session that launched the run opens the report for the author.

The template's example data is fictitious and neutral ("User A", "Item A"). Do not reuse any of it.

### Fields

| Field | Origin |
|---|---|
| `meta.example` | always `false` |
| `meta.concept`, `meta.version`, `meta.date` | `config.md` and the run date |
| `meta.panelSize` | "lean panel" or "full panel", in the report language |
| `meta.composition` | the actual panel, for example "8 users, 4 experts and 2 adversaries" |
| `meta.domain` | domain from `config.md` |
| `meta.type` | `"concept"`, `"system"` or `"change"`, from `config.md`; changes the sentence at the top of the report |
| `meta.usersLabel` | what the domain calls its users ("Users", "Players", "Customers"), in the report language |
| `meta.language` | the language from `config.md` (e.g. `English`, `Brazilian Portuguese`) |
| `summary` | 3 to 5 conclusions from the moderator, one sentence each |
| `dimensions` | those in `config.md`, with the same `id`, in round order. The **last** one colors the seats of the table at the top of the report (willingness to try or to accept) |
| `users[]` | `id`, `name`, `profile` (one line), `model`, final `scores`: round 2 scores for that round's dimensions; for round 1 dimensions (clarity and curiosity), the score revised in round 2 when the persona revised it, otherwise the round 1 score; `understood`, `attracted`, `putOff`, `dropOut` (one sentence each, from rounds 1 and 2) |
| `tensions[]` | disagreements from the debate and from round 2: `title`, `evidence`, `severity` (1 to 3), `for` and `against` with `who` (ids) and `text`, `proposal`, `loss`, `experiment`. Reactions to a revenue model go here |
| `risks[]` | `title`, `category` (`design`, `audience`, `production`, `scope` or `market`), `severity` and `likelihood` (1 to 3), `description`, `who` |
| `strengths[]` | `title`, `description`, `who` |
| `experts[]` | `id`, `role`, `opinion`, `mainProblem`, `recommendation` |
| `adversaries[]` | `id`, `role`, `arguments[]` with `title` and `text` |
| `scenarios[]` | round 3: `situation`, `outcome`, `classification` (`"hypothesis"` or `"proven problem"`) |
| `hypotheses[]` | `hypothesis`, `test`, `signal`, `priority` (`high`, `medium` or `low`) |
| `launch` | optional; omit it if it was not asked. `title`, `intro`, `recommendation`, `reasons[]`, `preferences[]` (`who`, `where`), `caveats` |
| `list` | optional; omit it if inactive. `title`, `order[]` with `name`, `comment`, `first` (ids), `rejected` (ids); `note` with the conflicts found and what stayed **[not verified]** |
| `gaps[]` | everything the panel could not evaluate for lack of specification |
| `limits[]` | 2 to 4 sentences from `diversity.md` on the limits of this run (anchoring, convergence, order effect) |
| `labels` | optional in English; **required, with every key**, when `meta.language` is not English. See below |

Conventions:

- Scores from 1 to 5, integers, "the higher, the better for the project".
- **Enum values stay in English** whatever the report language: `evidence` only accepts `"observation"`, `"hypothesis"` or `"proven problem"`; `classification` only `"hypothesis"` or `"proven problem"`; `priority` only `high`, `medium` or `low`; `category` one of the five above; `meta.type` one of the three above. The page shows them through the labels.
- Every `who`, `first`, `rejected` and `preferences[].who` uses ids that exist in `users`, `experts` or `adversaries`.
- All free text (summary, titles, descriptions, names, comments) is written in the report language.

### Report labels

The template holds a second JSON block, `<script type="application/json" id="default-labels">`, with every interface string in English: section titles and intros, buttons, legend, the names of the evidence values, priorities and risk categories, the risk axis names, the footer, the example-data notice. Composed strings use `{placeholders}` (for example `"metaLine": "Evaluated on {date} by a {panelSize} of {composition}."`); keep every placeholder when translating.

- The page uses `labels[key]` from the data when present, and the default otherwise.
- When `meta.language` is not English, copy **every** key of the `default-labels` block into `labels`, translated into that language. `report.py` reports an error if a key is missing or if `labels` has a key the template does not know.
- Never edit the `default-labels` block: it is part of the template, and the script checks that it stayed identical.
